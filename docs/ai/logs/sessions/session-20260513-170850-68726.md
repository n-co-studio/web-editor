## Goal
Restore reliable typing in the chrome-extension's inline text editor. Pressing Space while editing a `<button>` or `<summary>` was ejecting the operator out of edit mode on the first space character — the operator reported the symptom as "shortcut keys disrupting typing." Diagnosed and fixed in-session.

## Diagnosis (Query mode)
The session opened as `taskdef-query` for diagnosis before the operator authorized the implementation.

- Session 144's keystroke-hijack guard at `index.ts:1716` (`if (textEditor?.isActive()) return;` at top of `handleGlobalKeydown`) was confirmed intact in source AND in the compiled `dist/content.js`. The reported symptom is therefore NOT a regression of the session-144 fix.
- Root cause is a separate mechanism: `<button>` and `<summary>` natively synthesize a click event when activated by Space. That click reaches `selection/hover.ts:159` `handleClick`, which has no `textEditor`-active guard, and calls `selection.select()` → `activateToolForElement()` → `textEditor.cleanup()` at `index.ts:990` — ejecting the editor.
- The `handleClick` consumer is intentionally NOT guarded against `textEditor.isActive()` because real mouse clicks during text edit are supposed to commit-and-select-new. The fix must therefore happen at the synthesis source (the keydown that generates the synthetic click), not the click consumer.

## Changes Made
- `packages/chrome-extension/src/content/editing/text.ts` — Added module-level `ACTIVATE_ON_SPACE = new Set(['BUTTON', 'SUMMARY'])`. Added a new `else if` branch in `TextEditor.editElement()`'s keydown handler: when `e.key === ' '` and `ACTIVATE_ON_SPACE.has(element.tagName)`, call `e.preventDefault()` (suppressing the browser's Space-activation behavior, and therefore the synthesized click) and `document.execCommand('insertText', false, ' ')` to insert the literal space at the caret. Other tags in `TEXT_TAGS` retain native space handling.
- `docs/ai/logs/session-log.md` — Added Session 30 entry (consolidated log; per-session file is this document).
