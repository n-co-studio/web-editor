## Why

Three strands converged on one branch ahead of 0.3.0. The repo-OS template had
moved on and the local tree held a stale sync that had to come out before the
real one could land. The landing page was rebuilt against an updated Figma
design and repositioned to lead on MCP. And an accessibility and token audit
had produced a large set of changes that needed reviewing rather than trusting.

## What changed

**Template sync (Part A).** The stale `c555fc3` sync was discarded first: 39
modified files restored, 6 additions unstaged and deleted, leaving `.claude/`
and `docs/ai/governance/` clean and the 80 product files untouched. Then
`origin/main` was merged — a fast-forward to `29c2ff2`, taken only after
confirming zero overlap between the 165 files main touched and the 80 in
flight. `remote.template.tagOpt=--no-tags` was set after a `git fetch template`
pulled 125 template tags into the local repo; they were deleted.

**Landing page.** Rebuilt against Figma 52:3788 across several design
revisions. A shared `Stepper` component replaced repeated step markup; the
hero palette was retuned to the logo's spectrum; tab states were taken from
the Figma component set (52:3865) rather than guessed; bold weights were
unified through `--fw-strong`. Copy throughout now leads on MCP, which is the
actual differentiator — competing visual editors generate a prompt to paste,
while this dispatches a batch to the user's own MCP server.

**Store assets.** The five white-ground screenshots were replaced by four
dark-ground ones, with the promo tile and store icon re-cut to match. The
store listing's short description was rewritten to lead on MCP and is
byte-identical in `docs/store-listing.md` and `manifest.json`.

**Theming misses found in review.** Six raw colour literals in
`content/editing/insert-panel.ts` and one each in `content/tokens/snapping.ts`
and `content/selection/panes/console-pane.ts` were panel chrome that the audit
had missed. They are not the same class as the deliberately unthemed on-page
indicators (`SELECTION.ring`, `HANDLE_COLORS`, `DROP_INDICATOR`), which are
mode-coded and must stay fixed because they are drawn over pages of unknown
colour. The giveaway in each case was a sibling property on the same element
already being themed. Two were real defects rather than cosmetic:

- `insert-panel.ts` used `#10b981` as a tab underline and selected-item border.
  It measures 2.54:1 on the light panel, under the 3:1 WCAG 1.4.11 requires of
  a non-text indicator. `--fe-insert-text` already carried the per-theme value.
- `snapping.ts` set a swatch border to the themed `OVERLAY.swatchBorder` on
  construction, then **overwrote** it with raw `rgba(255,255,255,0.3)` on
  `mouseleave` — so hovering a swatch once left it permanently borderless on
  the light panel. A state bug, not only a theming one.

A third variant was found by code review and is the one worth remembering,
because the audit itself introduced it. `measure-overlay.ts` and
`multi-select.ts` had been switched from a fixed `#3b82f6` to the **themed**
`OVERLAY.info` — the inverse mistake. Both draw on the page, so the same
measurement rendered in a different colour depending on a panel setting, and
the distance label (white on the frame colour) fell from 3.68:1 to 2.54:1 in
dark mode. Each element also ended up with a themed border over a fixed
translucent fill. Fixed by adding `MEASURE_INDICATOR` to `shared/constants.ts`
as an explicit on-page constant, with the label on `#1d4ed8` (6.7:1 with
white) rather than on the frame colour.

The lesson for the next audit: "theme the colour" is not the rule. The rule is
that panel chrome is themed and on-page indicators are fixed, and a mechanical
sweep can break it in **both** directions.

`BOX_MODEL` was examined and deliberately left alone. Its text roles are
themed while its fills are raw `rgba(…, 0.20)`, which looks half-finished but
is correct: translucent fills composite over the themed panel background and
adapt on their own, whereas opaque text cannot.

**SDK bump and the advisory.** `@modelcontextprotocol/sdk` `^1.25.2` →
`^1.32.0`, folded into this branch for the critical `proxy-addr` advisory
(GHSA-jqcg-44mw-7w3h). It reaches consumers through SDK → express, so it is
not dev-only.

The bump alone did **not** clear it, which is what this session initially
assumed and the security sign-off caught. The SDK moved to 1.32.2, but
`express@5.2.1` still resolved `proxy-addr@2.0.7`, inside the vulnerable
`>=1.1.0 <2.0.8` range — a transitive pin a direct-dependency bump does not
move. `npm audit fix` was needed on top, and now resolves 2.0.8. Prod-path
advisories went from 6 to 1.

The one left is `zod` (GHSA-mrhx-c7xc-m3w5, high, memory exhaustion on
oversized collections). It is **not fixable from here**: the fix is zod 4.6.7,
a major bump, and `@modelcontextprotocol/sdk@1.32.2` pins zod 3.x — so
`npm audit fix --force` would break the SDK rather than patch it. It waits on
upstream SDK support for zod 4. Exposure is limited: the MCP server binds to
localhost and the advisory needs an attacker-supplied oversized payload.

## Security review and remediation

An adversarial review was run against the 0.3.0 candidate after the release
commits. It found one chain that mattered, and I verified every headline claim
in the code before acting rather than relaying the report.

**The chain.** The bridge gates connections on the `Origin` header alone, and
the allowlist accepts any `localhost`/`127.0.0.1`/`::1` origin on any port.
That is the page being edited, so script on the developer's own dev server
passes it — with the extension neither installed nor active. Once connected,
`saveDataUrl` chose both the directory and the extension of a file written
into the project: `resolveAssetDir` rejected `..` but not dot-directories and
tried the bare path as a candidate, and `assetExt` took the extension verbatim
from the caller while `guessExtFromMime` turned any MIME sub-type into one. So
`/.github/workflows/x.png` with `text/html` wrote a YAML or HTML file into a
directory GitHub executes on push. `confineToProject` held throughout — the
write stayed inside the repo — which is the point worth remembering: inside
the repo is not the same as harmless.

**What was fixed** (`fe59ab6`): asset writes are now image/video only, with a
MIME allowlist, an extension allowlist, a magic-byte check and an SVG script
screen; dot-directories are rejected; `guessExtFromMime` is deleted. The
message handler is wrapped and diffs are shape-checked, so a single malformed
message no longer kills the server. `sourceFile` is validated on ingest and
the tool result now labels page-derived content as untrusted in-band. The
HACK-003 sanitizer was also hardened — its `javascript:` test missed
`java<tab>script:` and leading control characters, SVG `animate`/`set` could
rewrite an href after inspection, and nested template content was never
walked. 29 regression tests added.

**What was deferred, and why.** The `Origin` weakness itself (KL-4) needs
either the socket moved into the service worker with a pinned extension ID, or
a pairing secret — a cross-package protocol change with the same four-way
version-skew problem HACK-008 had. Operator decision: ship 0.3.0 with the
impact reduced and do the authentication work as its own release. After
`fe59ab6` a client reaching the bridge gets information disclosure and
nuisance rather than code execution.

Two workflow findings (GT-6, GT-7) are in `.github/workflows/`, a governance
path not editable in child mode. Operator decision: fix upstream in
`repo-OS-template` so every child benefits and the lock stays meaningful.

**Three review rounds, and each one broke the previous fix.** That is the part
worth recording, more than any individual finding:

- Round 1 defeated three of the four fixes in `fe59ab6`. The MIME and the
  extension were validated separately so they did not have to agree; the
  allowlist was a truthiness check on a plain object, so `constructor` passed;
  the crash was contained but the poison persisted, because `isValidDiff` was
  shallow and a numeric `batchId` threw in a `localeCompare` sort, survived to
  disk, and was re-admitted on restart; and the `sourceFile` check was a shape
  check, so any string ending in `.tsx` was a free-text channel.
- Round 2 found that the fix for round 1 had introduced two more. Exempting
  `notes` from the untrusted framing — on the reasoning that the designer types
  them — created a trusted channel, because the extension appends a page-built
  element reference to every note. And the screening walk written for HACK-012
  had a `__proto__` bypass that reopened the HACK-013 poison pill on the import
  and restore paths.
- Round 3 found the per-diff containment added in round 2 was wrapped around
  the wrong call: the screening walk sat one line outside it, so a depth bomb
  still killed the batch. It also showed, by mutation testing, that most of the
  fixes were not pinned by their tests — removing the guard left the suite
  green.

The lesson is the mutation test, not the findings. Tests written alongside a
fix tend to restate it. Round 3's fixes were each checked by reverting the
guard and confirming a test fails; reverting the try placement fails two, the
depth cap one, the note normalisation two, the symlink guards one.

**Deferred to 0.3.1, deliberately:** KL-4 (bridge peer authentication) and
KL-6 (structured note refs) are one protocol change across two independently
versioned packages, with the same four-way skew problem HACK-008 had. KL-7
collects the smaller items. Operator decision 2026-10-27: ship 0.3.0 with the
impact reduced and do the protocol work as its own release.

**Worth carrying forward:** the misleading comment at `bridge.ts:539-553`
asserts the allowlist "blocks drive-by connections from an arbitrary web page
open in the same browser". It is true of a remote origin and false of the dev
page, and it is the most likely reason this survived two earlier security
passes. A comment that overstates a control is worse than no comment, because
the next reviewer checks the comment.
