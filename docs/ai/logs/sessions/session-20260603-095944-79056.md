# Session 20260603-095944-79056 — Image dedup: stop duplicating existing repo assets on media-source pick

## Brief
Operator report: when setting an image's source via the media properties panel / file
picker, selecting an image that is ALREADY present in the target project's public images
directory causes the Frontend Editor to write a duplicate (renamed) copy and pass it
through the MCP, instead of referencing the original on-disk file. Goal: reference the
existing file; do not upload duplicates.

## Root Cause
`packages/mcp-server/src/bridge.ts` `saveDataUrl()` always generated a unique
`uploaded-{timestamp}-{rand}` filename and wrote a new file for every decoded data URL,
with no existence/dedup check. The frontend file picker re-reads ANY picked file as a
base64 data URL — including files already in the repo — so the server was the only place
able to detect the duplicate. The frontend cannot reliably know the repo's on-disk layout.

## What Shipped

### `packages/mcp-server/src/bridge.ts` (+85 / −7)
- Imports `createHash` (`node:crypto`) and `readdir` (`node:fs/promises`).
- New `DEDUP_EXTS` static set — media extensions considered during the existence scan.
- `saveDataUrl()` now: computes SHA-256 of the decoded buffer; calls new
  `findExistingAsset()` to look for a byte-identical file already in the resolved target
  asset directory and, on a match, returns that existing project-relative path WITHOUT
  writing; otherwise writes a content-hash-named file (`uploaded-<hash12>.ext`) and skips
  the write if that exact file already exists (idempotent re-upload).
- New private `findExistingAsset(buffer, hash, targetDir)`: non-recursive scan of the
  target dir, cheap `size`-then-SHA-256 comparison, returns the existing web path or null.
- The dedup scan is best-effort: wrapped in try/catch and falls back to write-new on any
  error; the caller `extractDataUrls` already try/catches `saveDataUrl`, so the diff
  pipeline never breaks.

No frontend changes, no WebSocket/MCP protocol changes, no new dependencies.
