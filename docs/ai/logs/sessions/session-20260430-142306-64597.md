# Session 147 — 2026-05-03 — Carry CSS Rule Provenance Through to MCP

**Status:** complete
**Decisions:** none
**Branch:** `feat/rule-source-provenance-v2` (merged into `main`)

## Goal
Investigation question: when the user edits a property at one viewport in the live editor, does the captured diff identify the *original* CSS rule that owned the property (so a downstream agent could edit it in-place inside its `@media`/`@layer` scope), or does it just record "selector + new value"?

Investigation result: the inspector already extracts full rule context (`mediaQuery`, `layerName`, `sourceHref`, `specificity`) into `MatchedRule`, but the `DiffBuilder` threw it away. `PropertyChange` was just `{ property, fromValue, toValue, fromToken?, toToken?, unit? }` — no rule pointer. So edits made inside `@media (min-width: 1024px)` arrived at the agent as unscoped tweaks, leading the agent's safest move to be appending a global override that shadows the responsive rule. Edits also silently leaked across viewports.

## Root Cause
`packages/chrome-extension/src/content/index.ts` edit call sites called `diffBuilder!.build(info, changes)` with `info: ElementInfo` (selector + sourceFile/Line + bounding rect) and never invoked `getMatchedRules()` to identify which rule currently sets the property. The MCP server (`get_pending_visual_changes`) is a pure pass-through, so once the data was lost at diff-build time, downstream had no recourse.

## Changes Made
- `packages/shared/src/diff.ts` — Added `RuleSource { selector, sourceHref, sourceIndex, specificity, isInline, mediaQuery?, layerName? }`. Added optional `source?: RuleSource` field to `PropertyChange`.
- `packages/shared/src/index.ts` — Re-exported `RuleSource`.
- `packages/chrome-extension/src/content/inspection/css-rules.ts` — Added `findOwningRule(rules, property)` (cascade-correct: `!important` > specificity > source order, with inline winning unconditionally) and `toRuleSource(rule)` (caps `Infinity` specificity at finite sentinel `10000` so JSON roundtrips cleanly).
- `packages/chrome-extension/src/content/batching/diff-builder.ts` — Constructor now accepts an optional `RuleSourceResolver = (element, property) => RuleSource | undefined`. `build()`, `buildAttribute()`, `buildWithRelatedChanges()` accept an optional `element?: Element` and call the resolver per change in a new `enrich()` helper. Source resolution is best-effort: silently skipped when resolver/element absent.
- `packages/chrome-extension/src/content/index.ts` — Constructed `DiffBuilder` with a resolver that calls `getMatchedRules(el, undefined, host)` (excludes the extension's shadow-DOM styles via the host), runs `findOwningRule`, and converts via `toRuleSource`. Wrapped in try/catch for robustness. Updated all 12 property-change call sites (devtools panel, multi-select, handles, typography, colors, dimensions, spacing, position, media, effects, appearance, multi-select toolbar) to pass `el` through.
- `packages/mcp-server/src/server.ts` — Extended `get_pending_visual_changes` description to document the `source` field, instruct the agent to edit existing declarations in-place inside their `@media`/`@layer` scope (rather than appending overrides), and to cross-reference `source.mediaQuery` against `context.breakpoint` when deciding whether new declarations should be wrapped in a media block.

## Follow-ups
- The toggle-manager's state-simulation override sheet is not excluded from the resolver (PropertiesPane owns it lazily). At edit time it's typically empty, so the precision cost is small — but worth threading the dependency if a user reports stale source attribution after using state simulation.
- `relatedChanges` in `buildWithRelatedChanges` get the source for the *primary* element only; the `RelatedChange.element` (different element) does not get its own source resolution. Acceptable scope cut — related changes typically apply new declarations (e.g. `isolation: isolate` on a parent) where no existing rule owns the property.
- `prompt-serializer.ts` (clipboard markdown) was deliberately not updated per operator's direction ("not too bothered about the human-readable Markdown"). The raw JSON in the HTML comment now carries `source` automatically because `serializeToPrompt` embeds the full diff objects.
- Smoke test: open the extension on a page with responsive rules, edit a property whose source rule lives inside `@media (min-width: 768px)`, inspect the MCP `get_pending_visual_changes` payload, confirm `changes[].source.mediaQuery === "(min-width: 768px)"`.
