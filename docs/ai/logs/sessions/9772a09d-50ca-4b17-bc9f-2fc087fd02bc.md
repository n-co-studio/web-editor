# Session — partial revert of any-site activation (hotfix)

- **Session ID:** 9772a09d-50ca-4b17-bc9f-2fc087fd02bc
- **Type:** hotfix
- **Branch:** feature/revert-any-site-gating
- **Date:** 2026-10-11

## Why

Operator decision, taken to keep the Chrome Web Store review short ahead of
launch: an extension that can inject into any page the user clicks the icon on
invites a longer permissions review than one whose content script is confined to
`localhost`. The capability added in 8299672 is being withdrawn for the 0.2.0
submission, not abandoned.

## What changed

8299672 bundled two separable things. They were treated differently here.

**(A) The capability — reverted.** The localhost-only gating from a2ff026 is
restored: `isSupportedPage()` in `content/index.ts`, `getLocalDevTabId()` and
`renderUnavailable()` in `popup/popup.ts`. `shared/page-support.ts` and its test
are deleted, since nothing referenced them once the popup stopped gating on
`isInjectableUrl`. Every documentation claim that the editor runs on non-localhost
pages is back to localhost-only.

**(B) The agent-boundary disclosure — kept.** 8299672 also corrected the claim
that "no data leaves your machine". That claim was never true of the *agent* the
MCP server hands edits to: most agents forward what they read to a model
provider, and that is as true on a dev server as anywhere, because the payload is
identical. Reverting it would have put a false privacy claim back into a store
listing and privacy policy, which is a review risk rather than a review
shortcut — the opposite of the reason for this change. So
`docs/privacy-policy.md` keeps "What your agent sees", and SECURITY.md, both
READMEs, the store listing and the demo guide keep the corrected wording.

The retained text was reframed to drop every premise that depended on the
withdrawn capability. Where it used to say "you can now point the editor at any
page, including a production site you are logged into", it now makes the point
that still holds: a local dev server is frequently pointed at a seeded database,
a staging copy or a production dump, so the page being edited may carry real
records regardless of its hostname.

Also restored: the CHANGELOG entries for the two-column toolbar and the
off-screen toolbar fix, which 8299672 had happened to bundle in and which a clean
revert would have silently deleted. Those features are unrelated and still
shipped. The session log for the 8299672 session was likewise restored after the
mechanical revert deleted it — session logs are append-only records of work that
genuinely happened.

## Verification

- `tsc --noEmit` clean (extension and demo app)
- 153/153 extension tests pass — down from 160, exactly the 7 `page-support`
  assertions that went with the deleted test file
- Full-tree literal search for `page-support`, `isSupportedPage`,
  `getLocalDevTabId`, `isInjectableUrl`, "any site", "any website": no stale
  source or documentation references. The only remaining hits are in governance
  log artifacts, which are historical records and correctly left alone.
- Store zip rebuilt from a cleared `dist/` and `dist-zip/`, then verified by
  string inspection rather than assumption: `popup.js` and `content.js` now
  contain the localhost-gate strings ("Open a localhost dev page to use it",
  "Not a local development page") and zero any-site markers. 20 files, no source
  maps.

The zip that existed before this session (built 7 Oct) was confirmed to be the
**any-site** build. This is worth recording because the manifest cannot tell the
two builds apart — it is byte-identical between them, since the any-site path ran
through `activeTab` granted by the toolbar-icon click, never through
`content_scripts.matches`. Inspecting `manifest.json` suggests a localhost-only
extension in both cases; only the compiled popup distinguishes them.

## Follow-up

The deployed site at `nco.studio/web-editor/` is still the pre-8299672 build, so
its "where it runs" copy already matches this revert. Its privacy page, however,
predates the agent-boundary disclosure and does not carry it. Redeploying
(`npm run deploy:site`) is needed before submission, because the store listing
points reviewers at that privacy URL.
