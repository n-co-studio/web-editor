# Data Models & API Contracts

## Entities

### VisualDiff

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| id | string (uuid) | yes | Unique diff identifier — generated by the extension before sending |
| timestamp | string (ISO 8601) | yes | When the edit was made |
| element | ElementInfo | yes | Identifies the edited element |
| changes | PropertyChange[] | yes | List of property changes |
| context | PageContext | yes | Page URL, viewport, breakpoint, tab identity |
| status | "pending" \| "applied" \| "rejected" | yes | Processing state |
| sourceVerified | boolean | yes | True when data-source-* attributes are present on the element, false when missing |
| relatedChanges | RelatedChange[] | no | Property changes on other elements required by this edit (e.g., parent `isolation: isolate` for blend mode). Each entry identifies the affected element and the changes to apply. |
| reparentChanges | ReparentChange[] | no | Cross-container move operation applied as part of this edit. Populated only for reparent mode edits; empty for property-change-only diffs. |
| stylesheetChanges | StylesheetChange[] | no | Document-level CSS rules (`@keyframes`, `@supports`, `@media`) that cannot be expressed as element-inline declarations. Populated for scroll-driven parallax (feature-009) and for the mandatory `prefers-reduced-motion` zeroing rule that every **CSS** parallax mechanism (`fixed`, `transform-3d`, `scroll-driven`) emits. The `js-scroll` mechanism emits **no** reduced-motion `StylesheetChange` — its generated handler short-circuits on `matchMedia('(prefers-reduced-motion: reduce)')` instead (`ScriptBehaviorChange.respectsReducedMotion: true`). Empty for edits that need no stylesheet-level rules. |
| scriptChanges | ScriptBehaviorChange[] | no | Declarative descriptors for a bounded, reproducible-to-source JavaScript behavior. **v1 admits exactly one behavior — `parallax-scroll` (feature-009)** — under the constrained boundary allowance in `boundaries.md`. Empty for all CSS-only edits. |
| batchId | string | no | **Batch dispatch identity.** The `batch-YYYYMMDD-HHMMSS-xxxx` identifier minted by the content script at Apply-Changes click time (feature-004). Every diff in a single Apply-Changes click carries the **same** `batchId`. A reconnect retry re-sends diffs with the original `batchId` (membership is on the diff, not the transient send envelope). Absent on diffs produced before feature-004 batch identity was implemented — consumers treat absent `batchId` as membership in an ungrouped "legacy" batch (see [State Management / Persisted Queue](#state-management) for the degradation rule). |

**Relationships:** Contains ElementInfo, PropertyChange[], PageContext, RelatedChange[], StylesheetChange[], ScriptBehaviorChange[]

> The table above highlights the fields relevant to feature-009. `VisualDiff` additionally carries the existing optional parallel arrays `reorderChanges`, `insertChanges`, `removeChanges`, `groupChanges`, `attributeChanges`, and `textChanges` (see `packages/shared/src/diff.ts` for the complete interface). When extending `VisualDiff` for feature-009, add `stylesheetChanges` and `scriptChanges` alongside these — do not omit the existing arrays. feature-010 adds one further optional parallel array, `layoutContainers?: LayoutContainerDescriptor[]`, describing the editable-list containers referenced by any structural change in the diff (see [Structural Auto-Layout](#structural-auto-layout-data-fe-layout--layoutrole)) — additive-optional, no protocol bump.

**Assembly note:** The content script assembles the full VisualDiff — it generates the uuid, captures the timestamp, populates PageContext, sets sourceVerified, and sets the initial status to "pending". Feature-001 provides ElementInfo; feature-002 provides PropertyChange.

### ElementInfo

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| uid | string | no | **Canonical diff-targeting key** — the stable per-instance element identity, read from the `data-fe-uid` attribute (feature-006 stamps it at build, the content script assigns/repairs it at runtime; see [Stable Element Identity](#stable-element-identity-data-fe-uid)). Unique per DOM instance: a clone receives a **fresh** uid, so duplicate-then-edit no longer collides (issue #27). Optional only for backward compatibility — present whenever the element has been stamped; absent for `sourceVerified: false` nodes that have not yet been lazily stamped. When present, all change types (insert / reorder / attribute / text / reparent / remove) target the element by `uid`; when absent, consumers degrade to `selector` targeting. |
| selector | string | yes | CSS selector (most specific available). Fallback targeting key when `uid` is absent; also the human-readable locator. |
| tagName | string | yes | HTML tag name |
| textContent | string | no | First 80 chars (for identification) |
| sourceFile | string | yes | **Code-map hint, not identity.** Relative path from project root, from `data-source-file`. Locates the originating source for the applier; never used to distinguish element instances (clones share their origin's `sourceFile`). |
| sourceLine | number | yes | **Code-map hint, not identity.** Line number from `data-source-line`. Locates the originating source line; clones inherit the origin's `sourceLine`, so it is non-unique and must never key a diff (this collision is the root cause of issue #27). |
| instanceIndex | number | no | **Code-map hint, not identity.** Index for repeated elements sharing the same `sourceLine` (e.g., items inside `.map()` calls), from `data-source-index`. A best-effort disambiguator for source location only; `.map()` runtime instances still collide on it (every iteration shares one JSX line+index), so it is never authoritative identity — `uid` is. |
| attributes | Record<string, string> | yes | class, id, data-* (including `data-fe-uid` and `data-source-*`), aria-* |
| boundingRect | DOMRect | yes | Position and size at time of edit |
| assetPath | string | no | **Resolved served asset path** (issue #29). The element's own `src` / inline `background-image`, normalized through the [deployment-aware `src` rule](#deployment-aware-srchref-normalization) (single leading `/public` strip). Present **only** when the element resolves to a served asset — absent for non-image carriers — and **never** a `data:` / `blob:` URI (Brief 1 / #28 guarantees a served path, not inline bytes). Lets a downstream agent map `uid → /images/<file>` from the payload alone. See [Resolved asset reference](#resolved-asset-reference-assetpath--label). |
| label | string | no | **Short human label for the resolved asset** (issue #29): filename stem > `alt` > trimmed text (≤40) > tagName. Emitted **together with** `assetPath` (both present or both absent). |

> **Identity vs. location.** `uid` answers *"which element instance is this?"* (per-instance, unique, the diff key). `sourceFile` / `sourceLine` / `instanceIndex` answer *"where in source did this instance originate?"* (a shared code-map hint the applier uses to find or create source). The two are orthogonal: many DOM instances may map to one `sourceLine`, but each carries its own `uid`. See [Stable Element Identity](#stable-element-identity-data-fe-uid) for the full model.

| fromValue | string | yes | Computed value before edit |
| toValue | string | yes | New value after edit |

When present, a downstream agent edits that rule in-place instead of appending an override; absence means no existing rule sets the property. Defined in `packages/shared/src/diff.ts`. |
| allBreakpointSources | CrossBreakpointRuleSource[] | no | Context-only set of rules that set this property across all viewport `@media` blocks (each flagged `matchesCurrentViewport`). `StylesheetChange.elementChanges[]` entries carry `source` on the same terms as any other `PropertyChange` — the animation-`*` wiring should edit an existing rule in-place when one is present.

### ReorderChange

Moves a child element within the same parent container. Stored as a parallel array on `VisualDiff` (`reorderChanges[]`), separate from `PropertyChange[]`. The full runtime shape lives in `packages/shared/src/diff.ts`; this table is the **formal base contract** (previously the schema was footnoted to `diff.ts` only — see the [VisualDiff assembly note](#visualdiff)). `siblingAnchors` (issue #29) and `containerUid` (feature-010) are the additive-optional extensions layered on this base.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| type | "reorder" | yes | Discriminant literal. |
| fromIndex | number | yes | Child index within the container before the move. |
| toIndex | number | yes | Child index within the container after the move. |
| siblingSelectors | string[] | yes | Selectors for all siblings in the container at commit time — the canonical, always-present positional snapshot. |
| siblingAnchors | SiblingAnchor[] | no | Per-sibling anchors parallel to `siblingSelectors`, carrying `uid` + resolved `assetPath`/`label` per sibling (issue #29). Asset-resolution surface, **not** a uid-indexed identity register — see the [ReorderChange.siblingAnchors constraint](#reparentchange). |
| containerSelector | string | yes | CSS selector for the parent container the reorder happened in. |
| containerUid | string | no | **Editable-list container identity (feature-010).** `data-fe-uid` of the container the reorder happened in — the `uid`-keyed peer of `containerSelector`. When present, the applier resolves the container to source by `uid` (stable across re-render/reorder) instead of the positional selector. Additive-optional; absent for pre-feature-010 payloads and for containers with no `uid`, where the applier falls back to `containerSelector`. See [Structural Auto-Layout](#structural-auto-layout-data-fe-layout--layoutrole). |
| containerDirection | string | yes | Primary-axis direction of the container (`row` / `column` / `row-reverse`). For a wrapped/multi-line container it carries a space-separated ` wrap` suffix (`"row wrap"` / `"column wrap"`, issue #30) — the **first token is always the axis**, so a consumer reading only the first token is unaffected. |

> **Emitters.** `reorderChanges` is produced both by the reorder tool and by the reparent tool when the operator drops within the source container — a same-container drop is committed as a `reorderChange` (`fromIndex`→`toIndex`), never a `reparentChange` (see [`boundaries.md`](boundaries.md) → "Overlay containment"). Under feature-010 the reorder targets are the container's `layoutRole: flow` children only; `layoutRole: absolute` children (parallax / explicitly-placed) are **excluded** from `fromIndex`/`toIndex` math.

### GroupChange

Wraps 2+ sibling elements in a **new** flex/grid container. Stored as a parallel array on `VisualDiff` (`groupChanges[]`). The natural inverse is ungroup (unwrap). This table is the **formal base contract** (previously footnoted to `diff.ts` only). The runtime-created wrapper is the [uid → source mapping case (d)](#uid--source-mapping) — a container minted at runtime with a fresh `uid` and no build-time source origin.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| type | "group" | yes | Discriminant literal. |
| wrapperTagName | string | yes | Tag name of the new wrapper element the applier creates (e.g. `"div"`). |
| wrapperInitialStyles | PropertyChange[] | yes | Inline styles applied to the wrapper (e.g. `display:flex`, `gap`), so the created container is a conforming editable list. |
| wrapperUid | string | no | **Runtime-created-container identity (feature-010).** The **fresh** `data-fe-uid` minted for the wrapper at group time (the wrapper has no build-time origin). Carries the wrapper's identity into the diff so the applier can key the created source node and reconcile it after hot-reload via the [child-uid-set re-association, case (d)](#uid--source-mapping). Additive-optional. When authored/marked authoritative, the applier also stamps `data-fe-layout` on the created container. |
| containerSelector | string | yes | CSS selector for the parent container holding the siblings being grouped. |
| insertIndex | number | yes | Index in the parent where the new wrapper is inserted. |
| wrappedSelectors | string[] | yes | Selectors for the sibling elements being wrapped, in order. Under feature-010 these are `layoutRole: flow` peers; grouping requires a [real structural boundary](features/feature-010-structural-contract.md#the-flat-data-group-problem-acceptance-defining) — a container element and, for data-driven items, a nested data sub-array. |
| wrappedUids | string[] | no | **`data-fe-uid`s of the wrapped children**, positionally parallel to `wrappedSelectors` (feature-010). The `uid`-keyed peer of `wrappedSelectors`, following the same identity-vs-locator split as `siblingSelectors`/`siblingAnchors`. This is the **stable child-`uid` set** the [runtime-created-container round-trip (case d)](#uid--source-mapping) keys re-association on — carried on the `GroupChange` itself so re-association does not depend on a separate `LayoutContainerDescriptor` being present. Additive-optional; when absent, the applier falls back to matching the created container's `LayoutContainerDescriptor.childUids[]` in `layoutContainers[]`, else to `wrappedSelectors`. |
| prevSibling | SiblingAnchor \| null | yes | Sibling immediately before the wrapper's insert position, or null at index 0. |
| nextSibling | SiblingAnchor \| null | yes | Sibling immediately after the wrapper's insert position, or null at end. |

This table is the **formal base contract** (previously footnoted to `diff.ts` only).

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| type | "remove" | yes | Discriminant literal. |
| tagName | string | yes | Tag name of the removed element (for context / validation on apply). |
| containerSelector | string | yes | CSS selector for the container the element was removed from. |
| removedIndex | number | yes | Child index the element occupied before removal. |

### ReparentChange

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| type | "reparent" | yes | Discriminant literal |
| sourceContainerSelector | string | yes | CSS selector for the container the element moved from |
| sourceContainerUid | string | no | **Source editable-list container identity (feature-010).** `data-fe-uid` of the source container — the `uid`-keyed peer of `sourceContainerSelector`. Additive-optional; the applier falls back to the selector when absent. See [Structural Auto-Layout](#structural-auto-layout-data-fe-layout--layoutrole). |
| sourceIndex | number | yes | Child index within the source container before the move |
| targetContainerSelector | string | yes | CSS selector for the container the element moved into |
| targetContainerUid | string | no | **Target editable-list container identity (feature-010).** `data-fe-uid` of the target container — the `uid`-keyed peer of `targetContainerSelector`. Additive-optional; the applier falls back to the selector when absent. |
| targetIndex | number | yes | Child index within the target container after the move |
| siblingSelectors | string[] | yes | Selectors for all siblings in the target container at commit time |
| prevSibling | SiblingAnchor \| null | yes | Element immediately before the inserted position, or null if inserted at index 0 |
| nextSibling | SiblingAnchor \| null | yes | Element immediately after the inserted position, or null if inserted at end |

> **Sibling identity in reparent (issue #27).** Reparent-destination sibling identity is carried by `prevSibling.uid` / `nextSibling.uid` on the extended [SiblingAnchor](#siblinganchor-extended). The `siblingSelectors: string[]` array stays **selector-only** by design — it is a positional snapshot of the target container for context, not an identity register; do not add a parallel uid-indexed list. If uid-indexed sibling lists are ever needed, `siblingSelectors` is the extension point.
>
> **`ReorderChange.siblingAnchors` carries the same constraint (issue #29).** Although `SiblingAnchor` includes `uid`, `ReorderChange.siblingAnchors` is an **asset-resolution surface** (carrying `assetPath`/`label` per sibling), not a uid-indexed sibling register — do not treat it as a uid-keyed identity list. `siblingSelectors` remains the canonical, always-present list. In the current capture path `siblingAnchors` is emitted one-per-sibling (same length as `siblingSelectors`); when it is shorter or absent, present entries align **positionally from index 0** and an absent entry means that sibling carried no resolvable asset. See [Resolved asset reference](#resolved-asset-reference-assetpath--label).
>
> **`ReorderChange.containerDirection` wrap suffix (issue #30).** For a wrapped/multi-line container (flex `flex-wrap` ≠ `nowrap`, or a multi-track grid) the primary axis alone is insufficient — the layout is 2D. `containerDirection` therefore carries a space-separated ` wrap` suffix in that case, e.g. `"row wrap"` / `"column wrap"`. The **first token is always the axis** (`row` / `column` / `row-reverse`), so this is additive-compatible: a consumer that reads only the first token is unaffected, and a consumer that renders the whole string sees a still-human-readable value. No `WS_PROTOCOL_VERSION` bump. **Emitters:** `reorderChanges` is produced both by the reorder tool and by the reparent tool when the operator drops within the source container — a same-container drop is committed as a `reorderChange` (`fromIndex`→`toIndex`), never a `reparentChange` (see `boundaries.md` → "Overlay containment (issue #30)").

### StylesheetChange

A change that adds one or more **document-level CSS rules** that cannot be expressed as element-inline declarations — `@keyframes`, `@supports`, and `@media` blocks. Introduced by feature-009 (parallax editor) to carry pure-CSS scroll-driven animations (`@keyframes` + `animation-timeline`) and the mandatory `prefers-reduced-motion` zeroing rule that every **CSS** parallax mechanism (`fixed`, `transform-3d`, `scroll-driven`) emits. `js-scroll` carries no reduced-motion `StylesheetChange` — its handler short-circuits on `matchMedia` (`ScriptBehaviorChange.respectsReducedMotion`). Stored as a parallel array on `VisualDiff` (separate from `PropertyChange[]`), mirroring `relatedChanges` / `reparentChanges`.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| type | "stylesheet" | yes | Discriminant literal. |
| rules | StylesheetRule[] | yes | The document-level rules to add to the project's CSS. Order is significant — `@supports` fallbacks and `@media` overrides must follow the base rules they qualify. |
| elementChanges | PropertyChange[] | yes (may be `[]`) | Element-level longhands that wire the target element to the rules (e.g., `animation-name`, `animation-timeline`, `animation-duration`, `animation-fill-mode`, `animation-timing-function`). Applied to the element identified by `VisualDiff.element`. The array is **always present**, but is an **empty array** when the change adds only a `@media`/`@supports` rule with no new element wiring (e.g., a standalone reduced-motion rule) — an absent `elementChanges` is a protocol error, an empty one is valid. |
| reason | string | yes | Why the stylesheet rule is needed (e.g., `"scroll-driven-parallax"`, `"reduced-motion-zeroing"`, `"animation-timeline-fallback"`). |

### StylesheetRule

A single CSS rule block carried inside a `StylesheetChange`. `cssText` is the authoritative, ready-to-write rule text; the structured fields exist so a downstream agent can place, dedupe, or rewrite the rule without re-parsing `cssText`.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| ruleType | "keyframes" \| "supports" \| "media" | yes | The at-rule kind. |
| name | string | no | For `ruleType: "keyframes"`, the `@keyframes` identifier (e.g., `nco-parallax-7f3a`). Generated unique per edit to avoid collisions. Absent for `supports`/`media`. |
| condition | string | no | For `ruleType: "supports"` / `"media"`, the parenthesized condition (e.g., `(animation-timeline: scroll())`, `not (animation-timeline: scroll())`, `(prefers-reduced-motion: reduce)`). Absent for `keyframes`. |
| cssText | string | yes | Full rule text including the at-rule header and braces — the exact CSS a downstream agent writes into the stylesheet. |

### ScriptBehaviorChange

A **declarative descriptor** for a bounded JavaScript behavior. It does **not** carry literal JS source — it carries the *intent* and parameters from which Claude Code authors idempotent, reproducible source JS. Introduced by feature-009 for the JS-scroll-listener parallax mechanism. This is the only change type that crosses the CSS-only boundary, and it is constrained to a single enumerated behavior in v1 (see `boundaries.md`). Stored as a parallel array on `VisualDiff`.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| type | "script-behavior" | yes | Discriminant literal. |
| behavior | "parallax-scroll" | yes | Enumerated behavior identifier. **v1 admits this single value only** — the enum is the mechanism that bounds the boundary expansion; any other value is invalid and must be rejected by the consumer. |
| targetSelector | string | yes | CSS selector for the element the scroll-driven transform is applied to. |
| sourceFile | string | yes | Relative path from project root (from `data-source-file`) so Claude Code knows where to attach the behavior. |
| params | ScriptBehaviorParams | yes | Parameters the source author needs to reproduce the effect deterministically. |
| respectsReducedMotion | boolean | yes | Always `true` in v1 — the generated handler MUST short-circuit when `matchMedia('(prefers-reduced-motion: reduce)')` matches (WCAG 2.3.3). Carried explicitly so the contract is self-documenting and the QA gate is mechanical. |
| descriptor | string | yes | Human-readable statement of intent for the receiving agent (e.g., `"On scroll, translate <selector> vertically at 0.4× scroll velocity; disable under reduced-motion."`). |
| reason | string | yes | Why a script behavior (rather than a CSS mechanism) was chosen — typically `"js-scroll-parallax"`. |

### ScriptBehaviorParams

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| axis | "x" \| "y" | yes | Scroll axis the parallax tracks. v1 banners use `"y"`. |
| strengthFactor | number | yes | Scroll multiplier derived from `--parallax-strength` (the canonical dial). The transform offset per scroll pixel; e.g., `0.4` moves the element 0.4px per scrolled px. Range `0`–`1`. |
| throttle | "raf" | yes | The throttling strategy the generated handler uses. v1 fixes this to `"raf"` (one `requestAnimationFrame`-batched update per frame) so the descriptor cannot request unthrottled scroll work. |
| scrollSource | string | yes | Which element's scrolling drives the effect. `"window"` for page/viewport scroll; otherwise a CSS selector for the scroll container (e.g. an inner overlay or `<main>` that scrolls while `body` does not — common in SPAs). The generated handler MUST attach its scroll listener to this source rather than assume `window`. The editor resolves it from the operator's "scroll source" choice (auto-detected nearest scroll container, explicit page, or explicit container). The pure-CSS `scroll-driven` mechanism reflects the same choice in its `animation-timeline` (`scroll(root)` for page vs `scroll()` for the nearest container). |

### TextChange

A text content change — modifies the `innerHTML` (and therefore `textContent`) of an element. Stored
as a parallel array on `VisualDiff` (`textChanges`), separate from CSS `PropertyChange[]`. Introduced
with basic plain-text editing; extended by feature-012 with additive-optional markup fields.

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| type | `"text"` | yes | Discriminator literal — always `"text"`. |
| fromText | string | yes | Plain-text content of the element before the edit session (from `element.textContent`). Always present; serves as the fallback for consumers that do not process markup. |
| toText | string | yes | Plain-text content after the edit session (from `element.textContent` post-commit). Always present. |
| fromHtml | string | no | `innerHTML` of the element captured at the moment text edit mode was activated. Present only when the pre-edit element contained markup (i.e. `innerHTML !== textContent`) or when the operator performed inline styling during the session. Absent when the pre-edit content was plain text and no inline styling occurred. |
| toHtml | string | no | `innerHTML` after the edit session, after allowlist sanitization. Present when the committed result contains markup. Consumers MUST NOT crash when this field is absent — degrade to `toText`. |

**Additive-optional contract amendment** (feature-012): `fromHtml` and `toHtml` are new optional
fields. `fromText` and `toText` remain required plain-text fallbacks. Consumers that predate
feature-012 ignore the new fields — **no `WS_PROTOCOL_VERSION` bump is required**. This follows
the same additive-optional precedent as `batchId` and `layoutContainers` on `VisualDiff`.

**Allowlist.** When `toHtml` is present, its markup has been sanitized through the extension's
allowlist walker. Only the following tags survive, with **zero attributes**:

| Tag | Semantic meaning |
|-----|-----------------|
| `<strong>` | Bold (WCAG H49 — `<b>` is remapped to `<strong>` during toggle) |
| `<em>` | Italic (WCAG H49 — `<i>` is remapped to `<em>` during toggle) |
| `<u>` | Underline |
| `<s>` | Strikethrough |
| `<br>` | Line break (Shift+Enter) |

All other tags are stripped (text content preserved). All attributes are stripped.

#### Source Rewrite Semantics (TextChange)

How a downstream coding agent (Claude Code) reproduces a `TextChange` as project source.

**When `toHtml` is absent or equal to `toText`:** Replace the element's text content with `toText`
(plain string). This is the pre-feature-012 path; no inline markup involved.

**When `toHtml` is present:** The agent receives:
1. A one-line summary in the change description (plain text, may be truncated to 100 characters).
2. A fenced verbatim HTML block (never truncated) — the serialized `toHtml` value:

   ````
   Full HTML content (reproduce markup exactly):
   ```html
   <toHtml value here>
   ```
   ````

The agent MUST reproduce the inline markup in source, mapping tags 1:1:

| HTML tag | JSX / template source |
|----------|-----------------------|
| `<strong>` | `<strong>` |
| `<em>` | `<em>` |
| `<u>` | `<u>` |
| `<s>` | `<s>` |
| `<br>` | `<br />` (JSX self-closing) or `<br>` (HTML) |

**Interpolated expressions.** When the styled range in the DOM corresponds to content that is
interpolated in source (e.g. `{name}`, `{item.label}`), the agent MUST wrap the expression — not
inline its resolved value. Example:

- DOM: `Hello <strong>World</strong>` where "World" came from `{greeting}`
- Correct source: `Hello <strong>{greeting}</strong>`
- Incorrect source: `Hello <strong>World</strong>` (value inlined — breaks dynamic content)

Markup wraps only literal text runs without modification. The agent adds no `class` attributes,
inline `style`, or other attributes to the wrapper elements.

**Multi-line content.** `<br>` in `toHtml` maps to a line break in source. In JSX this is
`<br />`. In plain HTML this is `<br>`. The agent chooses the form appropriate to the target file.

### Source Rewrite Semantics (feature-009 change types)

How Claude Code reproduces each new change type as project source. The reproducible-to-source requirement is a boundary condition (`boundaries.md`): every mechanism must round-trip to maintainable source, not a runtime patch.

- **StylesheetChange → CSS source.** Claude Code writes each `StylesheetRule.cssText` into the stylesheet that owns the target element's styles (CSS module, global stylesheet, or the styled-block adjacent to the element's `sourceFile`), then applies `elementChanges` to the element's existing rule in-place (using each `PropertyChange.source` when present, exactly as for ordinary `PropertyChange`s). `@keyframes` names are written verbatim; the agent dedupes by `name` so re-applying an edit does not duplicate the keyframes. `@supports`/`@media` rules are written after the base rule they qualify.
- **ScriptBehaviorChange → JS source.** Claude Code authors an idempotent scroll handler from `descriptor` + `params` in the module that owns `sourceFile` (e.g., a `useEffect` in the React component, or a co-located effect hook), keyed by `targetSelector`. The handler MUST: batch updates with `requestAnimationFrame` (`params.throttle`), and short-circuit when `prefers-reduced-motion: reduce` matches (`respectsReducedMotion`). Re-application replaces the prior handler rather than stacking listeners. No literal JS crosses the wire — only the descriptor — so the generated source is reviewable and version-controlled like any hand-written code.
- **CSS-3D transform → existing `InsertChange.outerHTML` + `RemoveChange`.** The 3D mechanism needs no new change type: it reuses the existing replace pattern (a `RemoveChange` for the `<img>` plus an `InsertChange` whose `outerHTML` carries the perspective wrapper and inner element) already used by the current `parallax.ts` toggle. Its `@media (prefers-reduced-motion: reduce)` zeroing rule rides along as a `StylesheetChange`.
- **background-attachment: fixed → ordinary `PropertyChange[]`.** Inline declarations on the converted block (as `parallax.ts` already emits). Its reduced-motion zeroing rides along as a `StylesheetChange` (a `@media` rule cannot be inline).

**Protocol compatibility.** `stylesheetChanges`, `scriptChanges`, and `batchId` are additive, optional fields on `VisualDiff`. Consumers that predate them ignore unknown fields, so **no `WS_PROTOCOL_VERSION` bump is required** (same treatment as `reorderChanges` / `insertChanges` / `reparentChanges`, which were added without a protocol bump; the version remains `0.4.0`). The MCP tool surface (`get_pending_visual_changes`) returns the full `VisualDiff` unchanged. A `0.4.0` consumer that does not implement feature-009 will silently ignore `scriptChanges` / `stylesheetChanges` — this is intentional: the pending queue stays processable by Claude Code regardless of whether the MCP consumer is feature-009-aware. The `uid` / `anchorUid` / `anchorPosition` identity fields (issue #27) follow the same additive-optional rule — see [Protocol compatibility (uid + anchor fields)](#protocol-compatibility-uid--anchor-fields). `batchId` follows the same rule explicitly: a pre-batch-identity consumer that receives `batchId` simply ignores it and degrades to flat-pool processing — **no `WS_PROTOCOL_VERSION` bump is required**. The `AttributeChange.pendingUpload` / `AttributeChange.assetTruncated` asset fields (issue #28) follow the same additive-optional rule — see [No base64 in diffs — resolution to a served path](#no-base64-in-diffs--resolution-to-a-served-path-issue-28).

## Stable Element Identity (data-fe-uid)

> Ratified by the `stable-element-identity` task group (issue #27). The fields below are **additive-optional** schema extensions — see [Protocol compatibility](#protocol-compatibility-uid--anchor-fields). Implementation (stamping + applier resolution) lands in the build brief; this section is the agreed contract it builds against.

### Problem

Every tracked element was identified by `sourceFile` + `sourceLine`. When an operator **duplicates** an element, the clone is a DOM copy that inherits the **same `data-source-line`** as the original, so the two instances are indistinguishable in the diff payload. A follow-up operation on either twin (edit `src`/text, reorder, delete) can only reference the shared identity, so on replay the applier mis-assigns the edit and drops one twin — *"the image I duplicated first was deleted"*, *"the ordering is wrong"* (issue #27). `.map()` runtime instances have the same latent collision: N rendered nodes share one JSX `sourceLine` (+ `instanceIndex`).

### Model

`data-fe-uid` is a **stable, unique, per-instance** identifier carried as a DOM attribute and surfaced as `uid` on the diff-payload identity shapes. It is the **canonical diff-targeting key** for all change types. `data-source-*` attributes are demoted to **code-map hints** — they locate source, they never establish identity.

The `uid` field is added to every shape that currently identifies an element by `sourceFile`/`sourceLine`:

#### ElementInfo.uid
Documented in [ElementInfo](#elementinfo) — the canonical key for the edited element.

### uid → source mapping

How the **applier** (Claude Code, build brief) resolves a `uid` to a concrete source edit. The applier never trusts `uid` as a source coordinate — `uid` selects *which instance*, and the `sourceFile`/`sourceLine` **hint** (plus `outerHTML` for new markup) tells it *where in source* to act. Three cases:

| Case | Payload carries | Applier resolves to source by |
|------|-----------------|-------------------------------|
| **(a) Existing element** | `uid` + `sourceFile` + `sourceLine` hint | Edit the existing source node located at `sourceFile:sourceLine`. The `uid` confirms instance identity (and disambiguates when the operator edited one of several instances), but the edit targets already-existing source. |
| **(b) Clone / duplicate / paste** | **fresh** `uid` (≠ origin uid) + `outerHTML` of the cloned subtree + the **origin's** `sourceLine` as a hint | **Create new source** near the origin: the applier copies the origin's source node (located via the origin `sourceLine` hint), inserts the copy at the anchored position, and the new node's fresh `uid` becomes its stable identity for any later edit. The origin source is **not** modified. This is what makes duplicate-then-edit replay correctly — the twin has its own identity from creation. |
| **(c) Fresh insert** | fresh `uid` + `anchorUid` + `anchorPosition` + `outerHTML` (no meaningful origin `sourceLine`; `sourceVerified` may be `false`) | **Create new source** at the anchor: resolve `anchorUid` to its sibling's source location, then write the `outerHTML`-described markup `before`/`after` it (per `anchorPosition`). No positional `nth-of-type` resolution required. |
| **(d) Runtime-created container (group wrapper)** | **fresh** `wrapperUid` (minted at group time, no build-time origin) + the wrapped children's `uid`s (`GroupChange.wrappedUids`, falling back to the matching `LayoutContainerDescriptor.childUids[]`) + `prevSibling`/`nextSibling` anchors (feature-010 `GroupChange`) | **Create a new container in source** wrapping the grouped children: resolve each wrapped child's source node by its `uid` (cases a–c), then write a real container element (with conforming flex/grid styles and, when authoritative, a `data-fe-layout` stamp) around them at the anchored position — and, for data-driven items, introduce a **nested data sub-array** (the [flat-data structural-boundary rule](features/feature-010-structural-contract.md#the-flat-data-group-problem-acceptance-defining)). **Round-trip re-association:** after apply + hot-reload the dev-plugin stamps a *build-time* `uid` on the wrapper that differs from the runtime `wrapperUid`; the applier/reconciliation re-associates them by the **stable child-`uid` set** — the container whose `childUids[]` is a **superset of** `GroupChange.wrappedUids` is identified as the same logical container even under a new wrapper `uid` (superset, not exact-match, so a child inserted/removed inside the group before the reload does not defeat re-association; the grouped children keep their identities across the wrap). Re-association is attempted on the first post-reload `MutationObserver` tick; if no superset match is found, the wrapper is treated as a new anonymous container keyed by its build-time `uid` going forward. |

> **The runtime-created-container round-trip (case d).** The wrapper is the one node in a group operation with *no* pre-existing identity — it is minted live. Its `wrapperUid` is fresh (per the [fresh-uid-on-creation rule](#stamping-lifecycle)), so the *next* operation on the wrapper already has stable identity. The gap is only across the hot-reload boundary, where a build-time uid supersedes the runtime one; it is closed by keying re-association on the invariant that survives the swap — the set of child `uid`s the container wraps — backed by the [`data-fe-uid` reconciliation aids](#stamping-lifecycle) (lazy-uid walk + optional `WeakMap<Element, uid>` sidecar). This is the round-trip semantics feature-010 ratifies; the applier implements it in Brief 2.

> **Where the clone's origin `sourceLine` comes from (case b).** A clone is a DOM copy, so the new node inherits the origin's `data-source-line` attribute verbatim; its `ElementInfo.sourceLine` therefore already carries the origin's line. The capture layer MUST preserve that inherited `sourceLine` as the origin hint when it mints the clone's fresh `uid` — i.e. assign a fresh `data-fe-uid` **without** disturbing the copied `data-source-*`. This is precisely why `sourceLine` is a hint and not identity: two instances legitimately share it (origin and clone), and only `uid` separates them.

In every case the **fresh uid is minted at the moment of creation** (clone or insert) and stamped onto the new DOM node, so the *next* operation on that node already has stable identity — the failure mode in issue #27 (second operation references shared identity) cannot recur.

### Stamping lifecycle

Where each `data-fe-uid` value comes from, in priority order:

1. **Build-time stamp (primary).** The dev-plugin (feature-006) stamps a deterministic `data-fe-uid` on every JSX element at build, alongside `data-source-*`. Build-time stamping is the primary source because it **survives React reconciliation** — the attribute is part of the element's props/markup, so React preserves it across re-render rather than the content script having to re-stamp a recycled DOM node. For static (non-`.map()`) JSX, the build-time uid is stable for the element's lifetime.
2. **Runtime fresh-uid on clone / paste / duplicate.** When the content script clones a subtree (duplicate/paste), it mints a **fresh** uid for the new root **and every descendant** (deep walk) — a clone must never reuse the origin's uids, or the collision returns. Applied immediately on creation so the clone is independently addressable.
3. **Runtime lazy uid for `.map()` runtime instances and `sourceVerified: false` nodes.** One JSX line inside a `.map()` renders N runtime nodes that would share the build-time stamp (hash of file:line[:index]); a pure build-time uid is therefore **insufficient alone**. On first observation (MutationObserver / first selection) the content script lazily assigns a fresh per-instance uid to any tracked node that lacks a unique one — including nodes with no `data-source-*` (`sourceVerified: false`). Lazy assignment also covers elements rendered before the observer attached. **Pre-observation window:** between page render and the first observer sweep, `.map()` siblings transiently share a non-unique build-time uid. Brief 2 MUST complete the lazy-uid walk before any node is exposed for selection (e.g. run the initial walk synchronously when the observer connects, before enabling selection mode), so a diff can never capture a non-unique uid.
4. **Reconciliation resilience (option).** Because React can replace a DOM node while preserving logical identity, the content script MAY keep a **`WeakMap<Element, uid>` sidecar** so a uid can be recovered/re-stamped if the attribute is lost to a reconciliation that drops it. The attribute remains the wire-format source of truth; the WeakMap is a runtime durability aid, not a second identity system.

> **Why both build-time and runtime.** Build-time gives reconciliation-stable identity for the common static case for free; runtime assignment covers the cases the build plugin structurally cannot resolve to per-instance values (`.map()` fan-out, clones, unstamped/`sourceVerified:false` nodes). Neither alone is sufficient — see [*Alternatives Considered* in brief-stable-element-identity](features/brief-stable-element-identity.md#alternatives-considered).

### Deployment-aware src normalization

Captured `src`/`href` values are normalized so the path written to source is correct on apply (issue #27, weakness 2). Observed failure: captured `src="/public/images/foo.jpg"` (literal) where the served path is `/images/foo.jpg` (Next serves `public/` at the web root).

Normalization rule (applied at capture, before the value enters an `AttributeChange.toValue` / `outerHTML`):
- **Strip a single leading `/public` segment** from root-relative paths (`/public/images/foo.jpg` → `/images/foo.jpg`), reflecting that the framework serves the public directory at root.
- **Leave `data:` URIs untouched** (inline data has no deployment base).
- **Leave absolute `http(s)://` URLs untouched** (already fully qualified).
- Other root-relative and relative paths pass through unchanged.

This is a capture-layer concern (the value is normalized once, at the source of truth) so every downstream consumer receives an apply-correct path.

> **Framework scope.** The `/public`-at-root convention is Next.js / Vite-default behavior — the conventions v1 actually targets. The rule strips **at most one** leading `/public` segment, so a path that does not begin with `/public` is never altered (no over-stripping for frameworks that already serve at root). Frameworks that serve the public directory under a non-root base, or projects with a custom asset base, fall outside this rule; the strip is convention-gated — it is applied only when the element's resolved `data-source-file` (a known project context) is non-empty, and any unsupported convention degrades to the literal captured path. This limitation is intentionally narrow — it fixes the observed Next.js `/public` mismatch without claiming universal base resolution.
>
> **`sourceVerified: false` passthrough.** A `sourceVerified: false` element has no `data-source-file`, so the convention gate above is not met and the captured value passes through **literally** — unnormalized. An applier that encounters a literal `/public/…` path in an `AttributeChange.toValue` or `InsertChange.outerHTML` for a `sourceVerified: false` node should treat it as **expected passthrough, not a capture bug** (the capture layer could not confirm the project's asset convention without a source-file context). This is the same degrade-to-literal behavior described for unsupported conventions, surfaced explicitly here because it is the common shape for fresh inserts (uid → source mapping case (c)).

#### No base64 in diffs — resolution to a served path (issue #28)

Ratified by the `diff-capture-resource-model` task group (Brief 1, issue #28). A picked or embedded image must resolve to a **served path** (`/images/<name>`) in the diff — its bytes are never inlined as a `data:` URI. Base64 inline is the observed source of multi-MB batch bloat, and an inline blob is not an apply target (the agent cannot write a `data:` back to source as an asset reference).

**Capture layer (extension).** The media file picker emits a **blob URL** (`URL.createObjectURL`) for live in-DOM preview and carries a `pendingUpload { filename, mimeType, sizeBytes }` side-channel on the resulting `AttributeChange`, whose `toValue` is a provisional served path (`/images/<filename>`). No file bytes are read into the diff. `pendingUpload` and `assetTruncated?: boolean` are **additive-optional** `AttributeChange` fields (see [Protocol compatibility](#protocol-compatibility-uid--anchor-fields)) — no `WS_PROTOCOL_VERSION` bump.

**Server carriers (bridge).** Because base64 can enter a diff through more than one carrier, the bridge scans **all** of them at ingest and rewrites each to a served path: `attributeChanges[].toValue`, `insertChanges[].outerHTML` (clone/paste markup), and `background-image` `PropertyChange.toValue` in `changes` (`url(data:…)`). The single leading `/public` strip (above) is applied to every emitted served path, so a persisted asset is `/images/<name>`, never `/public/images/<name>`.

**Content-hash resolution for uncommitted assets.** When bytes are present (a residual `data:` carrier), the bridge content-hashes them (SHA-256): if a byte-identical file already exists in the resolved asset directory it is reused (no duplicate written); otherwise a new file is written, named `<stem>-<hash>.<ext>` (stem seeded from `pendingUpload.filename` when present, else `uploaded-<hash>`). The embedded hash makes re-selecting the same image idempotent. A file-picker pick transmits **no bytes** (blob-URL-backed) — its resolution is to an already-committed asset via `pendingUpload.filename`, with the provisional `/images/<filename>` path as the graceful fallback when the file is not found (the applier / operator reconciles it).

**base64 as a defined exception.** A `data:` URI surviving into an emitted value is **only** valid when the bridge could not persist it (a persistence failure is logged and the original value is passed through as a last-resort fallback). It is never the intended steady-state; consumers should treat a surviving `data:` as a degraded carrier, not a resource reference.

> **`blob:` in `outerHTML` — closed by Brief 2 (#29).** A file-picker pick sets the live DOM `src` to a blob URL (for preview). If such an element is duplicated **before** its served path is applied, the captured `InsertChange.outerHTML` carries a `src="blob:…"` — a page-local URL that is not resolvable server-side. The bridge rewrites only `data:` in `outerHTML`, so a `blob:` passes through unchanged. Brief 2 (#29) closes this: **every element reference now carries a resolved `assetPath`** (see [Resolved asset reference](#resolved-asset-reference-assetpath--label)) — and, critically, `assetPath` is populated only from a served path, so a `blob:` never lands there (it is filtered out at resolution). An applier that encounters a `blob:` in `outerHTML` ignores that reference and relies on the element's resolved `assetPath` (or the paired `AttributeChange.toValue`).

#### Resolved asset reference (`assetPath` + `label`)

Ratified by the `diff-capture-resource-model` task group (Brief 2, issue #29). Building on Brief 1's served-path guarantee (#28), **every element reference in the payload carries a resolved `assetPath` (a public-relative served path) plus a short human `label`** when — and only when — the referenced element resolves to an asset. This lets a downstream agent map `uid → /images/<file>` from the payload alone, with no working-tree correlation. The motivating repro (#29): a numbering note (`1,2,3,4 →` gallery images) carried uids but no `src`, so the ordering was unactionable; it now renders `N → /images/<file>` per item.

**Carriers.** `assetPath` / `label` are additive-optional fields on **`ElementInfo`, `NoteElementRef`, `SiblingAnchor`, and `ChildSnapshotEntry`** — i.e. the diff's element descriptor, note references, insert/reparent/group sibling anchors, and child snapshots. `ReorderChange` additionally gains an optional `siblingAnchors?: SiblingAnchor[]` parallel array (carrying `uid` + `assetPath`/`label` per sibling) alongside the existing `siblingSelectors: string[]`; `siblingSelectors` stays the canonical, always-present, selector-only list, so a consumer that ignores `siblingAnchors` is unaffected (this is the sanctioned use of the `siblingSelectors` extension point noted under [ReparentChange](#reparentchange)).

**Resolution rule.** `assetPath` is the element's own `src` / inline `background-image`, normalized through the [deployment-aware `src` rule](#deployment-aware-srchref-normalization) (single leading `/public` strip, source-file-gated). It is populated **only when an asset actually resolves** — absent (not empty / not `null`) on non-image carriers — and is **never** a `data:` or `blob:` URI (both are filtered at resolution: inline bytes and page-local blobs are not served paths). `label` derives as filename stem > `alt` > trimmed text (≤40) > tagName, and is emitted **together with** `assetPath` (both present or both absent). Resolution happens at capture / pick time while the DOM is live — the extension reads `src`; the server does **not** backfill `assetPath` for sibling / note references.

**`sourceVerified: false` interaction.** For a `sourceVerified: false` element (no `data-source-file`), the `/public` strip is not applied (convention gate unmet), so `assetPath` carries the literal captured served path — the same degrade-to-literal passthrough documented above. When the referenced element's asset was only recoverable via the bridge's content-hash resolution (a residual `data:` carrier persisted to `<stem>-<hash>.<ext>`), `assetPath` reflects that resolved `/images/<name>` when the capture layer observed a served `src`; it stays **absent** when no served path was resolvable at capture time (never a `data:` fallback). Additive-optional — **no `WS_PROTOCOL_VERSION` bump** (see [Protocol compatibility](#protocol-compatibility-uid--anchor-fields)); pre-#29 consumers ignore the fields and degrade to `selector` / `uid` targeting.

**Size cap + `assetTruncated`.** A single inline asset larger than the per-asset cap (4 MB) that **cannot** be deduplicated to a committed file is **truncated**, not inlined: for an `AttributeChange` the server sets `assetTruncated: true` and empties `toValue`; inside `outerHTML` / `url(data:…)` the oversized occurrence is replaced with an empty reference. An applier seeing `assetTruncated: true` must **not** write an empty `src` — it leaves the existing reference in place and surfaces the asset to the operator (an asset that large belongs committed to the project, not pasted through a diff). Dedup to an existing committed file wins regardless of size (the file is already in the repo).

### Protocol compatibility (uid + anchor fields)

`uid` (on `ElementInfo`, `SiblingAnchor`, `ChildSnapshotEntry`) and `anchorUid` / `anchorPosition` (on `InsertChange`) are **additive, optional** fields. Consumers that predate them ignore unknown fields, so **no `WS_PROTOCOL_VERSION` bump is required** — the version stays at `0.4.0`, exactly as `reorderChanges` / `insertChanges` / `reparentChanges` were added without a bump. A pre-uid consumer that receives these fields simply ignores them and **degrades to `selector` targeting** (and positional insert resolution) — the same behavior it has today. No required field is redefined; existing payloads remain valid. The `EXTENSION_HELLO` / `SERVER_HELLO` handshake is unaffected.

The `assetPath` / `label` fields (on `ElementInfo`, `NoteElementRef`, `SiblingAnchor`, `ChildSnapshotEntry`) and `ReorderChange.siblingAnchors` (issue #29) follow the **same** additive-optional rule — see [Resolved asset reference](#resolved-asset-reference-assetpath--label). A pre-#29 consumer ignores them and continues to target by `uid` / `selector`; no version bump.

The feature-010 structural fields — `VisualDiff.layoutContainers[]`, `LayoutContainerDescriptor`, `layoutRole` (on `SiblingAnchor` / `ChildSnapshotEntry`), `ReorderChange.containerUid`, `ReparentChange.sourceContainerUid`/`targetContainerUid`, and `GroupChange.wrapperUid`/`wrappedUids` — follow the **same** additive-optional rule (see [Structural Auto-Layout](#structural-auto-layout-data-fe-layout--layoutrole)). A pre-feature-010 consumer ignores them and degrades to `containerSelector` targeting and flat (all-`flow`) reorder behavior — the behavior it has today. No required field is redefined; the version stays at `0.4.0` and the `EXTENSION_HELLO` / `SERVER_HELLO` handshake is unaffected. The `data-fe-layout` DOM attribute is likewise additive: it is a new optional attribute the capture layer reads, never a change to an existing one.

## Structural Auto-Layout (data-fe-layout / layoutRole)

> Ratified by the `structural-auto-layout-contract` task group (Brief 1). The fields below are **additive-optional** schema extensions — see [Protocol compatibility](#protocol-compatibility-uid--anchor-fields). The conceptual model, the code-gen convention, and the acceptance-defining flat-data rule live in [feature-010](features/feature-010-structural-contract.md); this section is the authoritative wire contract they build against. Implementation (runtime signal + detection + the shared `packages/shared/src/layout.ts` module) lands in Brief 2.

### The editable-list signal (`data-fe-layout`)

An **editable list** is a container whose direct element children form a reorderable / groupable peer set. It is detected two ways, in priority order:

1. **Explicit signal — authoritative.** A **runtime-assigned or opt-in-authored** `data-fe-layout="flex" | "grid"` attribute on the container. When present, the container **is** an editable list of the named layout kind; the heuristic below is not consulted.
2. **Thresholded heuristic — fallback.** When no explicit signal is present: `getComputedStyle(el).display ∈ {flex, grid}` **AND** direct-element-child-count ≥ 2 **AND** child tag/uid homogeneity — children share a `tagName`, **or** share a `.map()` source-origin family, defined as **the same `data-source-file` + `data-source-line` pair** (siblings emitted by a single `.map()` call over one JSX line; `data-source-index` distinguishes the instances but the shared file+line is the family key). The gate suppresses **incidental flex wrappers** (nav bars, button rows, icon clusters) that are `display:flex` but are not editable lists.

**Why runtime / opt-in, never build-time.** The dev-plugin (feature-006) runs an AST pass at build and **cannot compute `display`** — the layout lives in CSS-module / Tailwind classes that resolve only at runtime. A build-time `data-fe-layout` would be a guess, not a fact. So the attribute is **stamped at runtime** from live computed style (behind the thresholded gate), or **authored opt-in** to mark a container authoritative. `data-fe-layout` carries the layout **kind** only (`flex`/`grid`) — it is not a duplicate of `display`, and its **absence means "fall back to the heuristic," not "not a list."** This mirrors the [`data-fe-uid` stamping split](#stamping-lifecycle): the plugin owns statically-computable facts; the runtime owns facts that exist only live.

The threshold constant (min child count = 2) and the homogeneity predicate are encoded once in `packages/shared/src/layout.ts` (`DATA_FE_LAYOUT_ATTR`, `parseLayoutSignal`), so capture and any convention validation share a single definition — see [feature-010 → Shared source of truth](features/feature-010-structural-contract.md#shared-source-of-truth--code-gen-convention).

### layoutRole (item classification)

Every **direct child** of an editable list is classified with an additive-optional `layoutRole`. **Wire carriage:** it is carried as an additive-optional `layoutRole?` field on the per-child context shapes — **`SiblingAnchor`** (used by `ReorderChange.siblingAnchors`, `GroupChange`, `ReparentChange`, `InsertChange`) and **`ChildSnapshotEntry`** (used by `InsertChange.childSnapshot`). `LayoutContainerDescriptor.childUids[]` is a `string[]` of uids and therefore does **not** itself carry roles; a child that is *itself a container* (`layoutRole: group`) additionally appears as its own `LayoutContainerDescriptor` in `layoutContainers[]`, so a group child's role is also recoverable by uid lookup, while `flow`/`absolute` **leaf** children carry their role only on the per-child shape. **Default when absent: `flow`** — so a consumer that ignores the field sees the pre-contract flat behavior (every child a reorder target), a clean degrade.

| `layoutRole` | Applies to | Reorderable | In gap-math | Diff-hidden | Notes |
|---|---|---|---|---|---|
| `flow` | Normal in-flow child (default). | yes | yes | no | The ordinary reorder/group target. |
| `absolute` | `position: absolute \| fixed` child, **and** an explicitly-placed grid child (`grid-area` / `grid-column` / `grid-row` placement). | **no** | **no** | **no — a visible peer** | The **parallax case**. Kept as a first-class, selectable, never-hidden peer, but **excluded from reorder index math and gap-math** because it is out of normal flow. Preserves feature-009's selector-anchored `ScriptBehaviorChange` contract — a parallax element is never swept into a `ReorderChange.fromIndex`/`toIndex`. |
| `group` | A direct child that is **itself** an editable-list container (nested flex/grid). | yes — **as an opaque peer** at the parent's level | yes (as one peer) | no | Exposed as a first-class peer; its internal children are one level down, described by a `LayoutContainerDescriptor`. Bounded to **one nesting level** in v1 ([`boundaries.md`](boundaries.md)). |

### LayoutContainerDescriptor

A self-describing descriptor for one editable-list container, carried on the additive-optional `VisualDiff.layoutContainers[]` array. A `layoutRole: group` child appears **twice, additively**: once as an opaque peer in its parent's `childUids[]` (so a parent-level reorder moves the whole group as one item), and once as its own `LayoutContainerDescriptor` (so the group's internals are self-describing **without a recursive tree on the wire**).

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| uid | string | yes | The container's own `data-fe-uid`. |
| layout | "flex" \| "grid" | yes | The layout kind, from `data-fe-layout` (explicit) or the resolved computed style (heuristic). |
| direction | string | yes | The container's `containerDirection` — primary axis, with the ` wrap` suffix for wrapped containers (`"row wrap"`, issue #30). First token is always the axis. |
| childUids | string[] | yes | `data-fe-uid`s of the container's direct children, **in visual order**. The parallel-array convention (idiomatic to `siblingSelectors`/`siblingAnchors`); lower agent parse cost than a recursive tree. A child that is itself a group appears here as its `uid` and has its own descriptor entry elsewhere in `layoutContainers[]`. |
| parentUid | string | no | `data-fe-uid` of the enclosing editable-list container. Absent for the top-level container. The single edge that reconstructs the (one-level) nesting from the flat `layoutContainers[]` array. |
| role | "flow" \| "group" | no | This descriptor's role in its parent list — `group` when this container is nested as a peer inside another editable list; absent/`flow` for the top-level container. **Distinct from `layoutRole`:** a `LayoutContainerDescriptor` describes a *container*, which is either a top-level list (`flow`/absent) or a nested peer (`group`) — it is never `absolute` (only non-container children are positioned peers), so this field deliberately omits `absolute` and is **not** the same type as the child `LayoutRole` union. |
| signalSource | "explicit" \| "heuristic" | yes | How the list was detected — `explicit` when `data-fe-layout` is already authoritative on the element, `heuristic` when detected from computed style. Tells the applier whether it must stamp `data-fe-layout` on codegen. |

**Considered alternative — recursive `leaf \| group` union on `childSnapshot`.** A discriminated tree where each child entry is a leaf or a group carrying its own children. **Rejected** in favor of the flat descriptor with explicit `childUids[]`: lower agent parse cost (no recursion), matches the existing parallel-array convention, and — because nesting is bounded to one level in v1 — a single `parentUid` edge suffices. The recursive union is the natural extension point if multi-level nesting is ever admitted (see [`boundaries.md`](boundaries.md) Future Considerations).

### Container identity on Reorder / Reparent

Two additive-optional `uid`-keyed container fields let structural moves target their container by stable identity instead of a positional selector (defined in the base tables above):

- **[`ReorderChange.containerUid?`](#reorderchange)** — the editable-list container the reorder happened in.
- **[`ReparentChange.sourceContainerUid?` / `targetContainerUid?`](#reparentchange)** — the source and target containers of a cross-container move.

In both cases the `uid` field is the canonical key when present, with the existing `*Selector` field as the always-present fallback — the same identity-vs-locator split the rest of the contract uses. The `GroupChange.wrapperUid` for a runtime-created container is the [uid → source mapping case (d)](#uid--source-mapping).

### Structural conformance — real boundary required

A group is only representable when it has a **real structural boundary**: a container element in the rendered JSX **and**, for data-driven items, a nested data sub-array — **not** flat sibling entries distinguished only by a presentational flag (e.g. `width:"half"`). The code-gen convention therefore governs the **data shape**, not only the JSX. This is the acceptance-defining "flat-data group problem" — its full statement, the Levantine root case, and the rule that an editor must not synthesize a phantom group over flat data live in [feature-010 → The flat-data group problem](features/feature-010-structural-contract.md#the-flat-data-group-problem-acceptance-defining).

All WebSocket messages use the following envelope structure:

```ts
}
```

### Message Types

| Type | Direction | Payload |
|------|-----------|---------|
| EXTENSION_HELLO | ext → server | `{ tabId: string, pendingDiffIds: string[] }` |
| SERVER_HELLO | server → ext | `{ knownDiffIds: string[], protocolVersion: string }` |
| VISUAL_DIFF_BATCH | ext → server | `{ diffs: VisualDiff[], batchNote?: string, batchId?: string }` — `batchId` is the authoritative batch identity for this dispatch (same value stamped on every diff in `diffs`); the server stamps it onto any diff missing it as a belt-and-suspenders. `batchNote` is the optional operator free-text note for this batch. |
| DIFF_ACK | server → ext | `{ diffIds: string[] }` |
| TOKEN_DATA | server → ext | `{ tokens: DesignToken[], sources: TokenSourceStatus[] }` |
| TOKEN_UPDATE | server → ext | Delta tokens (partial TOKEN_DATA payload) |
| COMPONENT_DATA | server → ext | `{ components: ProjectComponent[], sourceCount: number, failedCount: number }` — pushed on extension connect with the full current component registry |
| COMPONENT_UPDATE | server → ext | `{ components: ProjectComponent[], sourceCount: number, failedCount: number }` — pushed on every registry change with the full updated registry (per-file delta deferred) |
| KEEPALIVE | ext → server | `{}` |
| ERROR | bidirectional | `{ code: string, message: string }` |

## MCP Tool Definitions

#### get_pending_visual_changes
- **Purpose**: Returns all visual diffs and operator notes queued by the extension, with a lightweight batch summary index for cheap staleness scanning
- **Parameters**: `{ tabId?: string, batchId?: string }` — `tabId` filters by tab session; `batchId` filters to diffs belonging to a single batch (agents use this to retrieve one batch at a time without fetching the full queue)
- **Returns**: `{ changes: VisualDiff[], notes: PendingNote[], batches: BatchSummary[] }`
  - `changes` — flat array of all matching `VisualDiff[]`, each carrying `batchId` when present; agents group by `batchId` themselves (no nested restructure)
  - `notes` — flat array of `PendingNote[]` (preserved; removing this field would break existing agent consumers); each note carries an optional `batchId` correlating it to its batch (so the previously decoupled batch note re-associates)
  - `batches` — lightweight summary index `[{ batchId: string, batchNote?: string, createdAt: string, diffCount: number }]` for cheap batch enumeration and staleness scanning without fetching full diff bodies; ordered newest-first

#### acknowledge_visual_change
- **Purpose**: Marks a diff as applied (removes from pending queue)
- **Parameters**: `{ diffId: string }`
- **Returns**: `{ success: boolean }`

#### reject_visual_change
- **Purpose**: Marks a diff as rejected
- **Parameters**: `{ diffId: string, reason: string }`
- **Returns**: `{ success: boolean }`

#### get_design_tokens
- **Purpose**: Returns the project's parsed design tokens
- **Parameters**: `{ category?: string }` (optional filter)
- **Returns**: `{ tokens: DesignToken[], sources: TokenSourceStatus[] }`

#### resolve_to_token
- **Purpose**: Maps a CSS value to the nearest design token
- **Parameters**: `{ property: string, value: string }`
- **Returns**: `{ token?: string, exactMatch: boolean, nearestValue: string }`

#### get_token_drift_report
- **Purpose**: Returns session-scoped stats on custom value usage (values that did not match any design token)
- **Parameters**: none
- **Returns**: `{ escapes: { property: string, value: string, count: number, nearestToken?: string }[], summary: { totalEdits: number, tokenMatches: number, customValues: number } }`

#### get_queue_status
- **Purpose**: Returns lightweight queue status (active/closed, pending count, last update timestamp, latest batch id). Use instead of `get_pending_visual_changes` when only the queue state is needed (not full diff bodies).
- **Parameters**: `{}` (no input)
- **Returns**: `{ status: 'active' | 'closed', pending_count: number, updated_at: string, latest_batch_id?: string }` — `latest_batch_id` is the `batchId` of the most recently received batch (absent when no batches have been received, or when all diffs predate batch identity)

#### export_session
- **Purpose**: Writes the pending queue to a JSON file for archival or handoff
- **Parameters**: `{ outputPath?: string }` (defaults to `.nco-web-editor/session-export.json`)
- **Returns**: `{ path: string, diffCount: number }`

#### import_session
- **Purpose**: Loads a previously exported session file into the pending queue
- **Parameters**: `{ inputPath: string }`
- **Returns**: `{ imported: number, skipped: number, warnings: string[] }`

#### get_project_components
- **Purpose**: Returns the project-local component registry discovered by the MCP server
- **Parameters**: `{ nameFilter?: string }` (optional substring match on `componentName`, case-insensitive)
- **Returns**: `{ components: ProjectComponent[], sourceCount: number, failedCount: number }`
- **Notes**: Editor-agnostic — uses only generic working-directory contracts; no Claude Code or VS Code-specific assumptions. Component discovery is driven by `nco-web-editor.componentRoots` in the target project's `package.json` (or the default convention-gated roots). See feature-008 for full discovery semantics.

## State Management

- **Approach**: In-memory state in MCP server process with light file-based persistence
- **Key state shapes:**
  - Pending queue: `VisualDiff[]` — checkpointed to `.nco-web-editor/pending-queue.json` on each update, cleared when all diffs acknowledged. Each diff carries `batchId` when present; `batchId` rides on the persisted diff automatically with no migration or version bump required.
  - Pending notes: `PendingNote[]` — stored alongside the pending queue in `.nco-web-editor/pending-queue.json`. `PendingNote` gains an optional `batchId?: string` field correlating the note to the batch whose `VISUAL_DIFF_BATCH` envelope carried the matching `batchNote`. When the bridge receives a `batchNote` with a `batchId`, the stored `PendingNote` records both.
  - **Legacy `pending-queue.json` degradation:** Diffs and notes written before batch identity was implemented will not have a `batchId`. No migration code is run, no version bump is issued, and no queue file is rewritten. Legacy diffs pass through in the `changes` array of `get_pending_visual_changes` unchanged (with no `batchId` field). The `batches` summary index **omits** legacy diffs entirely — they are not grouped under a synthetic `"legacy"` entry. Consumers MUST NOT crash when `batchId` is absent on a diff in `changes`.
  - Token registry: `Map<string, DesignToken[]>` — rebuilt on file change, pushed to extensions
  - Component registry: `Map<string, ProjectComponent>` keyed by `importPath` — built at MCP server startup from convention-gated scan, rebuilt per-file on chokidar file change (300ms debounce), full registry pushed to all connected extensions on connect (`COMPONENT_DATA`) and on update (`COMPONENT_UPDATE`). Not persisted across server restarts (re-derived on next startup).
  - Token drift counters: session-scoped Map tracking custom value usage, reset on server restart
  - Connection state: WebSocket client tracking with tab IDs
  - Extension-side persistence: queue persisted to `chrome.storage.session` — survives page reloads and service worker suspension, cleared on browser close
  - Crash recovery: MCP server restores queue from `pending-queue.json` on restart. Extension restores from `chrome.storage.session` on page reload.
